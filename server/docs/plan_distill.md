# 蒸馏区（`distill/`）设计

> 状态：**已实现**（2026-11-08）。代码见 `server/src/distill/`，测试 `distill.test.ts`（39 条）。
> 关联：[plan_reflections_chat.md](plan_reflections_chat.md) §12.3、§11、§8。

## 0. 为什么需要这份文档

计划里第三期只有两行：

```text
1. `distill/meta` 与记忆联动。
2. 语义蒸馏的刷新策略（人工触发优先）。
```

但代码里 **`distill/` 只有目录约定，没有任何实现**：没有生产者、没有读取方、没有 `meta/overview.md` 的写入者。同时第二期遗留的「`distill/_archive` 生产者」也是同一个空洞——90 天 TTL 已就绪，但没有东西往归档里写，等于空转。

所以第三期不是「在现有蒸馏上加联动」，而是**先把蒸馏建出来**。这份文档定义：存什么、谁来写、什么时候写、读给谁、坏了怎么办。

---

## 1. 蒸馏区是什么，不是什么

| 是 | 不是 |
|----|------|
| 从大量原文里**压缩出来的派生物**，用于让 Agent 少读原文 | 真相源；原文才是，蒸馏随时可以丢掉重建 |
| 有明确**主题边界**的摘要（一篇对应一组来源） | 全文索引或向量库；这是给人/AI 读的散文，不是检索结构 |
| **AI 可写**（`writable` 已含 `distill`），写不弹框 | 用户手写的内容；用户改的是原文 |
| 单层、扁平、几十篇量级 | 深目录树；深了就得自建索引，那正是我们想避免的 |

**关键定位**：蒸馏是**缓存**，不是数据。任何「蒸馏文件丢了/过期了」的场景都必须退化为「读原文」，而不是报错。这条决定了后面所有失败分支的处理方式。

---

## 2. 目录与文件格式

```text
distill/
├── meta/
│   └── overview.md          # 全局蒸馏地图（只此一个文件）
├── reflections/
│   └── <主题>.md            # 从心得聚出来的主题摘要
├── knowledge/
│   └── <库名>/overview.md   # 某个知识库的总览
└── _archive/                # 被覆盖/删除的旧版本（90 天 TTL 已就绪）
```

> `distill/chat/` **不创建**（见 §3.1.1）：长会话摘要由已有的 `chat/compaction.ts` 负责，两者职责重叠。

### 2.1 文件格式：正文 + 结构化头

沿用记忆模块的成熟做法（`memory/store.ts` 的「正文 + `##` 分条」），不引入 JSON/YAML 前端：

```markdown
<!-- distill id:dst-a1b2c3 refreshed:2026-11-08T12:00:00.000Z -->

# 心得：Agent 记忆设计

## 摘要
（3~8 行散文，讲清这组原文在说什么）

## 来源
- reflections/inbox/2026-11-01-记忆分层.md
- reflections/inbox/2026-11-03-检索打分.md

## 有效期提示
原文改动时间晚于 refreshed 时，本摘要可能过期。
```

**为什么不用 front matter**：`distill` 是 AI 直接写的区，`write` 工具写的是纯文本。要求 AI 手写合法 YAML 头会经常写坏，而写坏了文件就解析不了——缓存坏掉不该导致读原文也失败。用一行 HTML 注释头，解析失败就当普通 markdown 全文使用。

**`id` 与 `refreshed` 是唯一必需字段**。缺 `id` → 视为「无主文件」（用户/AI 手写的普通笔记），**不参与自动刷新、不参与归档**，只当普通 markdown 读。这一条很重要：它让用户手动往 `distill/` 放笔记不会被系统覆盖。

### 2.2 `meta/overview.md`：全局地图

```markdown
<!-- distill id:dst-meta refreshed:2026-11-08T12:00:00.000Z -->

# 蒸馏地图

| 主题 | 文件 | 来源数 | 刷新于 |
|------|------|--------|--------|
| Agent 记忆设计 | reflections/agent-memory.md | 2 | 2026-11-08 |
| 索引机制 | reflections/index-design.md | 1 | 2026-11-05 |
```

**上限 2 KB**（与 `memory/focus.md` 同级）。超了说明主题该合并了，按 `importance`/来源数裁到最新 N 条。

`meta/overview.md` 是**唯一会被注入上下文的蒸馏文件**（§4）——注入一份地图，让 Agent 知道「有哪些摘要可用」，需要时再 `read` 具体文件。这与索引的「先看地图再下钻」是同一套思路。

## 3. 生产者：谁在什么时候写

**只有一个生产者：服务端**。Agent 不通过 `write` 直接生成蒸馏——理由与索引相同：多个写者就会漏更新 `meta/overview.md`。

### 3.1 触发方式：**人工触发优先**（计划原文）

| 触发 | 时机 | 行为 |
|------|------|------|
| **手动刷新（主路径）** | 用户在心得/文档面板点「刷新蒸馏」 | 对**当前作用域**重算；有差异才写 |
| 对话内按需 | Agent 调 `distill` 工具，指定来源 | 对该组来源重算一篇 |
| 后台补算（可选） | 启动后空闲时，对**过期且被读过**的摘要后台重算 | 只更新 `refreshed`，不新增主题 |

**明确不做自动全量重算**：那会在用户不知情时烧 token，且「摘要变了但我没让你改」很难解释。

### 3.1.1 两项已定取舍（2026-11-08 确认）

| 决定 | 结论 | 理由 |
|------|------|------|
| **专门的蒸馏前端页面** | ❌ **不做** | 蒸馏文件只是「能打开的文件」。做页面就要连带处理列表、删除、重建、空态一整套 UI，而它的读者是 Agent 不是人 |
| **`distill/chat/`（长会话滚动摘要）** | ❌ **暂不做** | 与已有 `chat/compaction.ts` 职责重叠；先看 compaction 够不够用，不够再补 |

这两条改动只影响 §2 的目录表与 §9 的实现清单——`distill/chat/` 目录不再创建，第 5 步的接口也不带会话参数。

### 3.2 失效判定（决定「要不要重算」）

不算 hash，只用时间与文件集合——与 L1 索引校准同构：

```text
过期 := max(来源文件 mtime) > refreshed
缺失 := 任何列在「来源」里的文件已不存在
```

`refreshed` 无法解析 → 视为过期但**不自动重算**，只在 `meta/overview.md` 标 `?`。

### 3.3 写入流程

```text
1. 收集来源（readdir + 只读需要的正文）
2. 调 LLM 生成摘要（失败 → 不写任何文件，保留旧摘要，记日志）
3. 写临时文件 → rename（原子）
4. 旧版本归档到 distill/_archive/<原有名>.<ISO 时间戳>-<随机>（保留最近 3 份，与记忆一致）
5. 重写 meta/overview.md
```

第 2 步失败**必须**保留旧摘要：蒸馏是缓存，宁可给过期内容也不给空文件。

## 4. 消费者：读给谁

| 读者 | 怎么用 |
|------|--------|
| **Agent 上下文** | 只注入 `meta/overview.md`（≤2 KB），与根索引同级进预算 |
| **Agent 工具** | `read`/`grep` 直接读具体摘要文件（无需新工具） |
| **前端** | 文档浏览器可**只读**打开 `distill/**`（便于人工核对 AI 到底总结了什么）；仍不做专门的蒸馏页面 |

**注入位置**：`buildSystemBlocks` 已有 `rootIndex` 与 `memoryText` 两个可变块。蒸馏地图加第三个块 `distillMap`，**优先级低于 memory、高于 policy**（越靠后越先被预算丢掉）：

```text
rootIndex > memory > distillMap > policy
```

这条顺序的依据：地图是「加速读」，丢了只影响效率；`policy` 丢了会影响行为安全，必须最后丢。

**默认关闭**，与 `injectRootIndex` 一致（`config.features.injectDistillMap`）。理由相同：地图白占 token，用户没要求就别塞。

## 5. 与记忆的联动（第 1 项的正题）

这是计划里唯一给出的需求，我把它拆成**三条单向规则**，避免双向耦合：

### 规则 A：蒸馏**不写**记忆

蒸馏的产物是派生摘要，不是「学到的偏好」。让它写 `longterm.md` 会让记忆被大量摘要文本污染，且参数一变就整段失效。

### 规则 B：记忆**不写**蒸馏

反过来也不行：`remember` 写的是「用户的偏好/事实」，进了蒸馏会把短句扩写成散文，等于二次失真。

### 规则 C：联动只在**注入层**发生——共用一个预算与一份去重表

具体是两件事：

1. **同一份内容不重复注入**。若某条记忆条目与 `meta/overview.md` 的某行指向同一来源文件，注入时只保留记忆（更短）。
2. **预算共享**。`memory + distillMap` 合计不超过 `MEMORY_TOKEN_MAX`（当前 1500）；超了先砍 `distillMap`（它是加速层）。

**这就是「联动」的全部**：不是互相写，而是在同一次上下文装配里**互斥与分账**。这样做的好处是任一侧坏掉都不影响另一侧——蒸馏算不出来，记忆照常注入。

## 6. 刷新策略（第 2 项的正题）

| 场景 | 策略 |
|------|------|
| 用户点「刷新蒸馏」 | 立即算，进度条/按钮 loading |
| Agent 调 `distill` 工具 | 立即算，结果进工具返回 |
| 后台 | `config.autoRefreshDistill`（**默认关**）打开后，启动跑一次：只处理 `stale` 且 30 天内刷新过的摘要，单轮最多 3 篇；跑失败静默 |
| 来源被删除 | 摘要保留，`meta` 里标 `missing`；用户可手动删 |
| 摘要文件被用户手改 | 有 `id` 的会被下次刷新覆盖；无 `id` 的永不碰 |

> **与计划的差异（有意为之）**：计划写的是「过期且最近 30 天被读过」，但**没有读取记录的数据源**
> ——蒸馏文件是普通 markdown，读它走通用 `read` 工具，没有钩子能记录「读过」。与其编一个假的
> 访问标记，实现改用可观测的等价条件：**只刷 30 天内刷新过的**（太久没动的主题大概率已无人关心）。
> 见 `generate.ts` 的 `autoRefreshStaleDistill`。

**不做定时重算**。定时重算的成本随语料线性增长，而用户对「后台偷偷烧钱」的容忍度是零。

### 6.1 已定的两项（见 §3.1.1）

1. **不做蒸馏前端页面**——蒸馏文件通过文档浏览器只读打开，不建专用列表/删除/重建/空态。
2. **不做 `distill/chat/`**——与 `chat/compaction.ts` 职责重叠，先看 compaction 够不够用。

---

## 7. `distill/_archive` 生产者（补第二期遗留）

按 §3.3 第 4 步：每次覆盖/删除摘要前先把旧文件归档到 `_archive/`，命名带 ISO 时间戳。这样第二期已实现的 90 天 TTL 才真正有数据可清。

保留最近 3 份（与 `memory` 的 `ARCHIVE_KEEP` 一致），第 4 份起直接删最旧的——不要指望 TTL 兜底，因为短时间内连续刷新会让 `_archive` 迅速膨胀。

---

## 8. 失败分支与退化（必须全部满足）

| 失败 | 退化行为 |
|------|---------|
| LLM 调用失败 | 不写文件、不动 `refreshed`，旧摘要继续可用；记日志 |
| 写文件失败 | 原子写保证不产生半截文件；`meta` 不更新 |
| `meta/overview.md` 写失败 | 具体摘要文件已写好，只是地图旧了；下次刷新自愈（与索引的 `indexSynced: false` 同构） |
| 摘要解析失败（头坏了） | 当普通 markdown 全文使用，不纳入自动刷新 |
| 来源全部消失 | 保留摘要，只标 `missing`，不自动删（用户可能只是临时移走） |

**总原则**：蒸馏是缓存，**任何蒸馏侧故障都不得让原文读取失败**。

实现时的两条补充约定（设计时没写死，实现后追加）：

- **`writeDistill` 不隐式重建地图**：地图只在 `generateDistill` / 显式 `rebuildOverview` 时重建。理由与索引一致——地图是「一批操作之后」的快照，逐次重写既浪费又容易和并发刷新互相覆盖。
- **`distill` 工具的风险档是 `session`**（与 `remember` 一致）：它只写 AI 可写区，同一会话首次确认后不再追问。
