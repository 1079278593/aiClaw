# 统一记忆方案：会话与内容分离 + 仿脑组织

> 状态：**方案设计，未按本文改代码。** 上下文治理（配额、心得单会话折叠）已提交；D4 已完成。
> 写于 2026-11，取代此前 `context_governance_plan.md` 里「只覆盖心得一条会话」的临时做法。
> 本文只讨论"内容怎么组织、怎么记住、怎么加强、怎么遗忘"。窗口装配的时序仍见
> `chat_loop_and_context.md`，配额常量仍见 `memory/types.ts`。
>
> 会话机制可以统一。聊天记录、人物档案、心得笔记仍是三种资料，不并成一种记忆。

---

## 0. 两个决定

**决定一：会话（session）与内容（content）是两个东西。** 会话是"身份 + 一段时间边界"，
内容是"被记录下来的东西"。会话可删，内容不随会话生死，除非它从未被固化出来。

**决定二：内容的组织模仿人脑，但只在"机制"层面仿，不在"形态"层面仿。**
仿的是分离、巩固、强化、遗忘这件事怎么发生；不仿的是"记忆是重构的、会自我虚构"这一半，
因为知识助手需要可以核对的原话。

下面先把两条决定各自说清楚，再给落地阶段。

## 1. 会话与内容分离

### 1.1 一条必须先解决的矛盾

「内容完整记录」+「会话可删」+「隐私模式删会话连内容一起删」，三者看似互相矛盾，
因为中间那一步（把内容从会话里取出来）被跳过没说了。

真实的关系是：

```text
会话原文  --固化-->  内容（可长期存活）
   |                     ^
   |                     |
   └─── 未固化 ──────────┘   （跟着会话一起消失）
```

所以**"二者不相关"不是天然成立的，是被"固化"这个动作造出来的**。固化就是解耦本身。
认清这一点之后，隐私模式不需要任何特例：**它就是"禁止固化"**，于是删会话自然连内容一起没了，
因为从来没有副本被造出来。

这和人脑完全对应，见 §2.1 的互补学习系统。

### 1.2 三条不变量

写代码前先把这三条定死，后面所有实现都是它们的推论。

**不变量 1（引用完整性）：任何固化出来的内容，必须记录来源。**
`sourceRefs: [{ sessionId, messageId, at }]`。不允许出现无来源的固化内容。
理由：这是事后审计"我为什么会这么想"的唯一依据，也是删除时能定位副本的前提。

**不变量 2（删除语义）：删会话只删"身份 + 未固化原文"。**
已固化的内容保留，其 `sourceRefs` 降级为 **dangling（悬空引用）**，界面显示"来源已删除"。
不级联删除。理由：已经确认要留下的结论，不该被一次误删会话清掉。

**不变量 3（隐私模式在读取侧执行，不只在写入侧）。**
标记为隐私的会话，`loadSessionForDerivation()` 直接拒绝，且后台固化任务读到它时静默跳过。
只在写入侧检查是不合格的：后台任务、蒸馏、索引重建都是独立的读取方，绕过是迟早的事。

### 1.3 存储布局

在现有 `getPaths()` 上增加，不推翻已有结构：

```text
conversations/<sessionId>.jsonl      会话原文（append-only，现状不动）
sessions/<sessionId>.meta.json       会话身份：title / profile / consolidation / privacy
content/entries/<contentId>.json     固化出来的内容条目（正文 + sourceRefs + 时间）
content/manifest.jsonl               内容清单：路径无关，只有 id/type/checksum/sourceRefs 摘要
memory/nodes/<nodeId>.md             原子记忆节点（见 §2.3，A-Mem 风格）
memory/edges.jsonl                   有向边：supports / contradicts / refines / derived_from
memory/themes/<theme>.md             主题层（跨会话，承载"反复问的同一个问题"）
memory/history/<nodeId>/<ts>.json    每次改写的旧版本（双时态，见 §2.5）
```

**为什么不做内容寻址（CAS）。** 内容寻址能天然去重、天然 GC，但要求会话文件不再自包含，
迁移量大且一旦哈希算错就全盘失效。折中：会话原文保持不变，固化条目里记 `checksum`，
需要去重时比对 `checksum` 即可，不改变读写路径。

### 1.4 隐私模式与"真删"

文件系统删除在多副本场景下是不成立的（备份、快照、`._archive`、NAS 回收站）。
要真的做到"删了就没了"，只有一条路：**加密后删除密钥（crypto-shredding）**。

```text
privacy 会话：原文用该会话独占的 key 加密写入
删除会话：删除 key（以及会话内固化的所有节点 key）→ 密文变成随机字节
效果：即使备份里还留着密文，也无法还原
```

这是唯一能在"备份仍然存在"的前提下成立的删除语义。代价：隐私会话不可被固化、
不可被索引、不可被蒸馏——这正好就是"仅限本次对话"的字面含义。

### 1.5 会话元数据

原来那个 `app_state.reflectionsSessionId` 单例指针连同它的四种用途一起拆掉：

```jsonc
// sessions/<id>.meta.json
{
  "id": "...",
  "title": "...",
  // 决定能力，不决定身份。三段判据：是否固化 / 是否保留 / 是否可见
  "profile": {
    "consolidate": true,      // 是否允许把内容固化出去（原「心得会话」= true）
    "fold": true,             // 是否做增量折叠（dialogue-fold.ts）
    "ephemeral": false        // 会话到期后是否真删原文
  },
  "privacy": false,           // true → 加密 + 禁止一切派生 + 不可索引
  "createdAt": "...",
  "lastActiveAt": "...",
  // 只保留「上次在哪」这一个指针语义，且允许有多条
  "pinned": false
}
```

关键改动：`GET /api/sessions` **不再过滤**，全部返回并带上 `profile`，由客户端分组。
服务端过滤是"一个入口绑定一种会话"的根因，拆掉之后"任意入口都能开新会话"才成立。

## 2. 仿脑组织

### 2.1 理论骨架：互补学习系统（CLS）

这是这一整套设计里唯一"有明确理论支撑、且已被工程验证"的部分，值得单独说清。

**McClelland, McNaughton & O'Reilly (1995)** 提出：大脑有两套学习系统分工，
原因是**灾难性干扰**（catastrophic interference）——如果新知识直接改同一套权重，
会覆盖旧知识。所以：

| 系统 | 学习速度 | 特征 | 后果 |
|---|---|---|---|
| 海马（episodic） | 快、一次成型 | 具体、依赖线索、相互干扰小 | 容量有限，会遗忘 |
| 新皮层（semantic） | 慢、需重复 | 抽象、稳定、可泛化 | 更新慢，抗干扰 |

两套系统通过**重放（replay）** 在离线时把海马的内容交错地（interleaved）教给新皮层。
交错是关键：不能一次性把新东西灌进去，必须和旧知识混合着练，否则仍会干扰。

**为什么这条理论对你这个项目是好消息：** 它直接给出了三条设计约束，而且是可验证的：

1. 必须有两层，且快的那层便宜、可删（对应会话原文）。
2. 慢的那层必须通过**调度**更新，不能实时改（对应固化队列）。
3. 更新必须**交错**（新条目要和已有同主题条目一起重写），不能只 append（对应 §2.4 的合并式固化）。

这条理论在持续学习工程里对应 experience replay / interleaved training，不是空谈。

### 2.2 机制映射表

只列能落地、且能验证的。每条都给"生物"、"代码怎么实现"、"怎么判断做对了"。

| 机制 | 生物 | 代码实现 | 判据 |
|---|---|---|---|
| 模式分离 | 齿状回把相似经历区分开 | 每条固化内容有独立 id + 当时的上下文锚点，**不合并相似项** | 问同一个问题的两次对话，能分别追溯回各自原文 |
| 模式补全 | CA3 用部分线索唤回整体 | 从线索节点出发做图扩散（PPR），而非只取最近邻 | 只给一个术语，能召回半年前那次的结论 |
| 系统巩固 | 睡眠期重放 | 空闲窗口触发的后台任务（sleep-time），与对话主流程分离 | 固化不阻塞任何一轮对话 |
| 再巩固 | 提取让记忆变得可改写 | 被检索**且被实际使用**的节点，允许更新并留旧版本 | 更新后能看到"这条改于何时、改前是什么" |
| 长时程增强 | 用得越多越强 | `used` 计数 + 间隔重复的稳定度 | 常被引用的条目排序稳定靠前 |
| 适应性遗忘 | 不用则弱化，但不消失 | 只衰减**排序分数**，不删正文 | 冷门内容仍能被精确关键词检索到 |
| 图式同化 | 新信息归入已有框架 | 新条目优先并入同主题，主题页加厚而非新增页 | 主题数增长远慢于会话数 |
| 工作记忆容量 | 约 4 个组块 | 就是上下文窗口的分块预算（现状五格） | 窗口不因记忆层增长而膨胀 |

### 2.3 原子节点（A-Mem 的可用部分）

**A-Mem (NeurIPS 2025)** 的做法值得直接借：每条记忆是一张**原子卡片**，
带结构化属性（上下文描述、关键词、标签），新卡片加入时检索近邻并由模型生成链接，
**同时允许更新邻居的上下文**——作者称之为 memory evolution，实质就是再巩固。

借鉴：

```jsonc
// memory/nodes/<id>.md 的头部
{
  "id": "nd-...",
  "created": "...",
  "updated": "...",
  "kind": "conclusion | question | fact | preference",
  "importance": "high | medium",       // 沿用现有两档，不扩
  "tags": ["..."],
  "sourceRefs": [{ "sessionId": "...", "messageId": "..." }],
  "accessCount": 0,
  "lastAccess": "...",
  "stability": 1.0                     // 间隔重复，见 §2.6
}
```

**不借鉴的部分：** A-Mem 允许新记忆随意改写邻居的上下文，这在个人知识库里是危险的
（一次误判会污染一批旧结论）。我们的约束：**邻居只能被"追加"链接，不能被静默改写；
改写正文必须走 pending 审批**（项目里已有 `pending/` 提议机制，直接复用）。

### 2.4 固化：什么时候把原文变成内容

**不要用定时器。** 定时器的问题不是不准，是它与"重要性"无关——重要的和不重要的同频处理，
既浪费又制造噪声。用四个增量信号：

| 信号 | 含义 | 触发 |
|---|---|---|
| S1 折叠推进 | 会话内已收进状态的段落（现成产物） | 每次 `foldDialogueState` 成功后，把「已定结论 / 未决问题」增量送进固化队列 |
| S2 用户显式 | 「记入心得」 | 立即排队，最高优先级 |
| S3 跨会话重复 | 同一主题在 N 天内被 ≥2 个**不同会话**命中 | 排队（这是"反复问同一个问题"的机械识别） |
| S4 空闲窗口 | 距上次交互 > X 分钟且队列非空 | 批量处理（sleep-time），可中断 |

S1 是成本最低的一环，而且**已经存在**：折叠强制产出「硬约束 / 已定结论 / 未决问题 / 重要事实」
四段，其中两段就是主题蒸馏的现成原料。固化器只消费这份增量，**永不回读整条会话**。

**合并式固化（交错）**：新内容进队列后，不是 append 一条，而是
`旧主题页 + 新条目 → 重写主题页`。这是 §2.1 里"交错更新"的落地形式，
也是"反复问的问题收敛到同一页"的机制。产出走 pending 提议 + diff 审批，不自动生效。

### 2.5 双时态：让结论的变化可追溯

要回答"当时这条结论是什么、现在这条结论是什么"，需要两个时间轴：

```text
valid_from / valid_to : 这条结论在现实里成立的时间区间
ingested_at           : 它被写进系统的时刻
```

新结论与旧结论冲突时，**不覆盖**，而是：旧条目 `valid_to = 新条目 valid_from`，
并加一条 `contradicts` 边。好处：

- 问"我当时怎么想的"能答对（按 `valid_from` 过滤）
- 问"现在怎么看"也能答对（只取 `valid_to = null`）
- 冲突是显式的，不会静默丢历史

**Zep / Graphiti** 是这个思路的成熟实现（时序知识图谱 + 双时态边），可以直接参考其
edge invalidation 的设计，不需要自己发明。

### 2.6 强化与遗忘

**强化**要绑"被使用"，不是"被检索"。注入进窗口但模型没引用，属于噪声共现，
给它加分会让系统自我强化错误（正反馈污染）。可观测信号只有两个：

1. 模型回复里引用了该条（`[[nodeId]]` 或文内提及）
2. 工具调用读取了它

命中这两者才 `accessCount++`、更新 `lastAccess`。

**用间隔重复而不是纯指数衰减。** 生成式智能体那套 `0.995^hours` 是纯时间衰减，
且**公开实现里有一个已确认的缺陷**：`retrieve.py` 按 `last_accessed` 升序排列后
把最大的衰减权给第一个元素，结果是"最久没被访问的记忆拿到最高 recency 分"，
方向是反的（见参考文献里的 issue）。所以：

- 抄它的**思想**（recency / importance / relevance 三因子），不抄它的数字和实现；
- 衰减改成按真实墙钟时间的半衰期；
- 稳定度用间隔重复（SM-2 简化版）：成功召回后 `stability *= factor`，
  衰减半衰期随 `stability` 拉长。这样"重要的越用越牢"是涌现出来的，不需要手调权重。

**遗忘只作用于排序。** 冷门内容的正文永远保留，精确关键词检索永远能召回到它。
"忘记"= 降低它在没有明确线索时冒出来的概率，不等于删除。

### 2.7 检索：三路并行 + 融合

单一向量检索在"精确事实"上并不差，而纯图检索在简单事实上**会退化**——HippoRAG 2 的论文
明确指出 RAPTOR / GraphRAG 这类结构增强方法在基本事实问答上有下降，它自己专门修掉这个问题。
所以三路都要，用 RRF 融合而不是加权求和（加权求和的权重无法解释，也无法停止调参）：

```text
关键词（BM25/精确）  ─┐
向量（近邻）          ├─→ RRF 融合 → 预算裁剪 → 注入
图扩散（PPR，从线索出发）─┘
```

预算按固定配比切给三路，避免某一路因分数尺度不同而淹没其他（这是 RRF 的已知问题，
用配额兜住）。图扩散只在有明确实体线索时启用，没有线索就退化为前两路。

## 3. 参考项目与文献

只列我核对过、且确实有可借鉴实现的部分。

**组织方式**

- **A-Mem**（NeurIPS 2025，[arXiv:2502.12110](https://arxiv.org/abs/2502.12110)）：
  齐特卡斯特式原子卡片 + 动态链接 + 邻居演化。借"卡片 + 边 + 演化"，不借"随意改写邻居"。
- **HippoRAG 2**（ICML 2025，[arXiv:2502.14802](https://arxiv.org/abs/2502.14802)）：
  把海马索引显式实现为开放知识图谱上的 Personalized PageRank（phrase 节点 + passage 节点）。
  这是"模式补全"最直接的工程对应，且论文自己验证了不牺牲简单事实问答。

**巩固时机**

- **Letta / MemGPT + sleep-time compute**（[arXiv:2504.13171](https://arxiv.org/abs/2504.13171)、
  [Letta 博客](https://www.letta.com/blog/sleep-time-compute/)）：
  把"改记忆"从对话智能体里拆出来，交给一个空闲时运行的后台智能体，共享同一份记忆块。
  这是"系统巩固在离线发生"的最干净工程形态——**固化不阻塞对话**这条要求就是从这里来的。

**检索打分**

- **Generative Agents**（[arXiv:2304.03442](https://arxiv.org/abs/2304.03442)）：
  recency / importance / relevance 三因子归一化求和，是这一族的设计原型。
  但注意公开代码与论文不一致且有方向性 bug（[issue #212](https://github.com/joonspk-research/generative_agents/issues/212)），
  不要照抄参数。

**双时态**

- **Zep / Graphiti**：时序知识图谱，边带 `valid_from / valid_to / ingested_at`，
  冲突用 edge invalidation 而不是删除。正好对应 §2.5。

**理论**

- **McClelland, McNaughton & O'Reilly (1995)**，*Why there are complementary learning systems
  in the hippocampus and neocortex*。这是"为什么必须两层、为什么必须离线交错更新"的来源，
  也是本项目最能站得住的理论依据。

## 4. 落地阶段

每一阶段都能独立发布、独立回滚。**不要跳阶段**，因为后面的依赖前面的不变量。
阶段 3、5、6 不与 0～2 捆在同一次实现里。固化质量没被用过之前，不要上自动合并。

已完成、不在本阶段表里：记忆四层配额、单会话增量折叠、工具结果归档。D4（先提交再动阶段 0）已完成。

### 阶段 0：拆单例（不改行为，风险最低）

- `app_state.reflectionsSessionId` → `sessions/<id>.meta.json` 里的 `profile`
- `prepareReflectionsContext` 判据从"id 等于那个指针"改成 `profile.fold === true`
- 迁移：读取时若 `meta` 不存在，回退旧逻辑并生成一份 `meta`（幂等）
- `GET /api/sessions` 停止过滤，改为返回 `profile`
- 桌面端切「心得 / 人物」不再隐含"这是另一种会话"。面板只设置默认 `profile` 和焦点（当前笔记路径、当前人物 id）

验证：现有测试全绿；旧心得会话行为不变；能同时开两条 `fold: true` 的会话。

### 阶段 1：内容库、删除语义、一条手动固化

- `content/entries` + `manifest.jsonl`，固化条目带 `sourceRefs`
- **只做信号 S2**：「记入心得 / 记入记忆」。不接折叠自动推进、不接跨会话重复、不接空闲批处理
- 删会话：原文进回收站（D1）、已固化条目保留、`sourceRefs` 标 dangling
- `privacy: true`：读取侧拒绝固化、蒸馏、索引、注入。这是本阶段的完成线

验证：手动固化一条 → 删会话 → 条目仍在且显示「来源已删除」；隐私会话不出现在任何派生读取里。
没有 S2，内容库是空的，删除语义无法被验证。

### 阶段 1b：真删（密钥方案定稿之后）

- 会话独占 key 加密原文，删除即删 key（crypto-shredding）
- 同一次设计必须写清：key 放哪、NAS/本机快照里会不会留下 key、轮换后旧密文怎么办
- 做不到这三件，就不要宣称"真删"。阶段 1 的读侧拒绝已经挡住正常路径

### 阶段 2：原子节点与边

- `memory/nodes` + `memory/edges.jsonl`
- 节点只能追加链接；改正文走 `pending/`，或进临时区并标「待确认」（D2），不静默覆盖
- 节点用 `sourceRefs` 指向会话消息、心得文件或人物条目。不把这三个目录收成一种节点库
- 折叠四段**仍不自动入库**。候选节点只来自 S2，或人在临时区里点确认

验证：同一问题两次对话产生两张卡片，各自能追溯来源，之间有边而不是被合并。

### 阶段 4a：离线检索实验（可与阶段 2 后半并行，不接窗口）

- 只在已有条目上对比：关键词；关键词 + 向量
- **不改** `buildMemoryInjection`，不和四层记忆的 7500 token 抢预算
- 图扩散（PPR）不做。没有稳定的边之前上图，简单事实会先变差

验证：一批固定问题里，精确术语不比纯关键词差；模糊问法有增益。差了就停，不进注入。

### 阶段 3：主题层与双时态（等 S2 用过、看清噪声后再做）

- `memory/themes/<theme>.md`，合并式固化（交错重写）
- `valid_from / valid_to / ingested_at`，冲突加 `contradicts` 边
- 每次改写写 `memory/history/<nodeId>/<ts>.json`
- 判据要持续看：**主题页数量的增长速度远慢于会话数**。近义主题暴涨就停，先修识别，不继续自动合并

验证：改变看法后，问"当时的看法"和"现在的看法"都能答对；误判的 `contradicts` 能人工拆掉。

### 阶段 4b：三路检索接进窗口

- 在 4a 不退化的前提下，加 PPR；无实体线索时退化为关键词 + 向量
- RRF 融合，三路用**固定条数配额**，不用可调权重
- 这时才和 `buildMemoryInjection` 共用预算池，并单独测"简单事实没有被图结果淹没"

### 阶段 5：固化调度

- 补上 S1（折叠推进）、S3（跨会话重复）、S4（空闲批处理）
- 后台任务可中断、幂等、失败不影响对话
- S1 默认只产生临时区候选，不直接改主题页。否则折叠什么都收，主题页变脏

验证：固化不阻塞对话；同一轮重复触发不产生重复内容。

### 阶段 6：强化与遗忘

- `accessCount` 只在"被引用 / 被工具读取"时 +1，被注入但不被用到不加分
- 间隔重复更新 `stability`，半衰期按墙钟时间、随稳定度拉长
- 衰减只作用于排序，正文不动

验证：常被引用的条目排序稳定；冷门条目在精确检索下仍可召回。

## 5. 明确不做的事

这几条比"做什么"更重要，因为都是同类系统里代价很高的坑。

1. **不做全自动改写身份层。** `user.md` / `focus.md` 是"你是谁"，只能人确认后改。
   让模型自动改身份层，等于让它悄悄改变自己的自我认知，出错无法追溯。
2. **不抄位置衰减。** 按索引位置衰减在突发使用下完全失真，必须用真实时间。
3. **不要让所有检索都走图。** 简单事实会退化（HippoRAG 2 论文已证明这一点）。
4. **不要用 embedding 等同于语义记忆。** 向量相似度只是线索之一，不是"理解"。
5. **不要让固化内容成为唯一事实源。** 原文是唯一可核对的事实，蒸馏层一律视为有损投影。
   要原话时，按 `sourceRefs` 把对应消息或文件片段读回窗口。
6. **不要在一个改动里同时动两件事。** 比如同一个提交里既改存储又改检索，出问题无法二分定位。

## 7. 三个模块：什么该统一，什么不该

上一版把聊天、人物、心得收成「同一种记忆的三种看法」。对照现有代码和主流做法之后，这个收法过头了。值得统一的是**会话**，不是这三份资料。

| 模块 | 它实际在做什么 | 该不该并进记忆节点 |
|---|---|---|
| 聊天 | `conversations/*.jsonl`，一次对话的原文 | 原文保持原样。只有人确认留下的结论才进 `content/entries` |
| 心得 | `reflections/*.md`，人写的笔记；AI 只读，改动走 `pending/` | 不并。笔记是人的文稿。记忆条目可以引用它，不能代替它 |
| 人物 | `people/<id>/` 的档案、简报、逐条记录；AI 在体积约束下直接改；删除进 `_archive/` | 不并。这是按人建档。对话里提到某人时，用边指向这个 id，不把档案改造成记忆页 |

值得做的只有一件跨模块的事：**拆掉「心得会话」这个会话种类。**

桌面端切到心得或人物时本来就不换会话（`architecture.md`：面板与会话无关）。例外出在移动端的 `reflectionsSessionId`：一条隐藏会话同时决定折叠、列表过滤、以及 join 时不更新上次位置。这是会话模型的漏洞，修它不需要改人物，也不需要改心得笔记的 ACL。阶段 0 只做这件事。

不值得做的：

- **不要把人物档案改成 pending。** `people/` 能被 AI 直接改，是有意的：整理一个人是高频、局部的操作，已经有「不能砍掉一半栏目、删除只归档」的约束。再套一层审批，人物模块会变难用，对「记住一条结论」没有帮助。
- **不要把人物原话和心得笔记放进同一次检索。** 别人说的一句、自己写下的一段、模型抽出的一条结论，混在一个排序里会互相污染。人物检索留在人物页；笔记检索留在笔记索引；记忆检索只查 `content/` 和以后的节点。
- **不要让 `distill/` 开始摘要对话和人物。** 蒸馏继续服务笔记和知识库。对话要留下的东西走显式记入，不走目录级摘要。

`sourceRefs` 允许指向消息、心得路径或人物条目，只为了能点回去。这是引用，不是把三个目录收成一个库。

## 8. 这个目标本身能不能做成

目标收窄为：会话可删，确认留下的结论不跟着删；结论能指回原句；隐私会话不被抄进记忆；以后能看出一条结论是被新结论接替的，而不是被盖掉。

主流系统没有把「聊天记录、实体档案、用户文稿」合成一个库。它们统一的是记忆的**层**，不是产品模块：

| 做法 | 来源 | 和本项目的关系 |
|---|---|---|
| 原文检索和显式记忆分开 | Letta：recall 搜历史消息，archival 只存有意写入的事实；核心块才常驻窗口 | 与阶段 1 一致。本项目已有常驻的 `user.md` / `focus.md`，相当于核心块，不必再造 |
| 抽出事实再决定新增、改写、删除或不动 | Mem0（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)） | 能做，但是每写一条都让模型裁决。裁决错了会悄悄改掉旧结论。本方案不把这种自动改写当默认 |
| 原文层、实体层、社区摘要层分开存，边带有效期 | Zep（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)） | 双时态和「实体指向原文」可以借鉴。Zep 是独立的图服务。本仓库是文件和 jsonl，做不出同等的图引擎，只做得出少量边和有效期字段 |

因此能在这份代码里落地的，是 Letta 那种分界，加上可选的引用字段：

- 阶段 0：会话不再分「心得种」和「聊天种」。改动面是 `app-state`、`prepareReflectionsContext` 的判断、会话列表过滤。人物和心得文件不动。
- 阶段 1：显式记入写入 `content/entries`，带 `sourceRefs`；删会话不删这些条目；隐私会话在读取侧被拒绝。这是新目录，不改三块现有读写。
- 阶段 2 起的图、主题重写、空闲巩固，都是在文件上模拟 Zep / HippoRAG。没有独立图数据库和评测集时，效果不稳定，不和 0、1 一起做。

做完 0 和 1 的实际效果：

- 从心得入口可以开多条对话，行为由会话自己的 `profile` 决定。
- 人点过记入的句子，会话删了还在，并能打开原来的那条消息。
- 没点过的内容随会话进回收站。
- 人物档案、心得笔记的编辑方式与现在相同。

做不到的，是模型自动维持一套始终正确、会自己合并主题、会在空闲时变得更清楚的长期记忆。那需要持续的抽取质量和人工抽查。Mem0 和 Zep 把这块做成了单独产品；放进当前服务里，只能做成「人点一次、系统负责别丢」。这就是这个目标在本仓库里的完成线。
