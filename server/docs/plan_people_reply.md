## 0. 使用场景

点开一个人，在这个人的界面里输入。输入可能是：

- 一个问题（「这句话怎么回」）
- 一段聊天记录
- 一段情境：里面有想法、有对话、有对情况的描述

模型要做的事：根据**这次输入**和**这个人已经入库的资料**，回答问题，并分析情况。

已拍板：

| 问题 | 结论 |
|---|---|
| 会话和内容是否分开 | 分开。会话可删；这个人的原文、简报、档案不删 |
| 会不会无限把历史塞进模型 | 文件可以变长；每一轮送给模型的历史不能无限变长 |
| 一个人几条对话 | 多条。一条对话对应一次分析 |
| 新对话带不带上一次的原文 | 不带。带档案、当前判断，以及简报的路径 |
| 模型回复要不要入库 | 不入库。回复只留在会话里 |
| 人物资料要不要自动更新 | 简报只追加。另有一份很短的「当前判断」，由整理整篇替换。档案不在自动路径里替换 |

## 1. 两份数据

```text
会话   conversations/<sessionId>.jsonl
       你和模型的来回。删会话只删这个文件，以及这份会话自己的折叠状态。

内容   people/<personId>/
       profile.md     档案（这个人是谁）
       digest.md      简报（已整理过的经过，是摘要不是原话）
       entries.jsonl  原文（你录入或贴进来的记录，一条一条）
```

模型这一轮的回复留在会话里。它不是这个人的事实。简报和当前判断只从已经入库的原文整理出来。

你贴进输入框的聊天记录和情境，是内容，不是会话。发送时先落入 `entries.jsonl`，再开始这一轮分析。这样会话删了，贴进来的记录还在。

## 2. 现在的代码差在哪

人物页没有自己的会话。`people.js` 切到人物面板时不换 `currentSessionId`，消息写进右侧那条全局聊天（`chat.js` 的 `sendMessage`）。

每一轮如果带了 `threadPath: people/<id>`，`chat-handler.ts` 会调用 `buildPersonContextSuffix`：

- 档案不超过 12000 字时整篇放进这一轮；超过则只给路径。
- 简报和原文只给路径，默认不整篇注入。模型要用工具读。
- 点「整理」时，只把 `organizedAt` 之后的新原文交给模型，结果经 `applyOrganizeResult` 写入 `digest.md`，并推进 `organizedAt`。

窗口预算在 `context-budget.ts`：装不下时从最旧的轮次丢，**不写成摘要**。文件里的旧消息还在，下一轮模型看不见。

折叠在 `dialogue-fold.ts`：待折叠内容超过 8000 token 时，把更早的轮次收成一份不超过 2000 token 的状态，原文不删。当时**只有** `app_state.reflectionsSessionId` 那一条会话会走它（`prepareReflectionsContext`），人物对话不走。阶段 3 已把判据改成 `session.fold`，见 §7。

输入框里贴的文字今天只会变成会话里的一条用户消息，不会写入 `entries.jsonl`。

## 3. 会话

一个人多条分析会话。每条会话在 jsonl 首行元数据里记下 `personId`。人物页只列出这个人的会话。

这些会话不出现在全局聊天列表里，join 时也不改写 `lastActiveSessionId`。否则从人物页返回聊天，会停在一次人物分析上。桌面 `people.js` 和移动端 `person_page.dart` 都走这条规则，两边现在都把人物消息写进当前全局会话。

新建一条时窗口里有：

- 系统提示（沿用人物页现有的称呼和阅读顺序）
- 档案（仍按 12000 字的规则）
- `current.md` 的全文（当前判断，有上限）
- 简报的路径；简报正文由模型按需读取，不把历次简报全部贴进首轮
- 这次要分析的输入（已经写入 `entries.jsonl` 的那几条，本轮作为用户消息）

不带入：

- 其他分析会话的消息
- 上一条会话的折叠状态
- 全局聊天里和这个人无关的历史

同一条会话里来回变长时再打开折叠，那是阶段 3。阶段 1 只把会话从全局聊天里拆出来，不改变折叠判据。折叠打开后，原文仍在这个会话文件里，窗口只保留折叠状态和最近 2 轮。判据到那时改为这条会话自己的 `fold: true`。心得那条旧会话同时写成 `fold: true`，行为与现在一致。

删会话：删除 `conversations/<id>.jsonl` 和 `dialogue-state.md` 里这一条的块。不改 `profile.md`、`digest.md`、`current.md`、`entries.jsonl`。

## 4. 入库

人物资料的自动更新只吃**原文**，不吃模型回复。回复里的策略、猜测、措辞建议留在会话里。删会话不影响已经写好的简报和档案。

**原文。** 用户在这个人的界面里发出的文字，先追加为 `entries.jsonl` 的一条（`kind=note`，保留原话），再发起分析。会话写入失败时，原文仍在。

**简报。** 原文落盘后跑整理，只看 `organizedAt` 之后的新原文。简报只在末尾追加一段，不重写旧段。没有可追加的正文时跳过，不推进 `organizedAt`。简报是经过，允许前后两段说法不一样。

**当前判断。** 同一次整理可以整篇替换 `people/<id>/current.md`，不追加。这份文件只回答「现在按什么判断来回复」，几行即可，上限 1500 字，超出则这次不替换。它不代替简报。写错了，简报里的旧段还在，人可以直接改 `current.md`。不走待应用，否则每次发送都要人点一次，自动更新等于没做。

**档案。** 自动整理不写 `profile.md`。档案仍只在人点「整理」且结果在 `<<<档案>>>` 后给出完整档案、并通过现有校验时才替换：栏目齐全、称呼不冲突、行数不少于原来的一半（除非标明精简）。行数校验挡不住把一句原话概括成性格标签，所以不让自动路径改档案。

不给每条判断打 explicit / inferred 标记。这个标记仍由同一个模型填写，不能当作校验。约束放在数据流上：自动路径只追加简报、只替换短的当前判断；档案靠人手点。

模型回复不进入以上三份文件。

## 5. 一次不要带太多

每一轮送给模型的内容只有这四块，都有上限：

| 块 | 上限 | 已有或新增 |
|---|---|---|
| 档案 | 12000 字，超出只给路径 | 已有 `PROFILE_INLINE_LIMIT`。每轮整篇注入会在档案变动时使前缀缓存失效，阶段 1–4 不改 |
| 当前判断 | 1500 字，整篇注入 | 新增 `current.md` |
| 简报 | 不默认注入全文 | 已有，只给路径 |
| 本轮用户输入 | 单条消息；过长仍整段保存到原文，注入前按现有单消息预算截断并注明原文在 `entries.jsonl` | 发送路径上补截断说明 |
| 本会话更早的来回 | 窗口剩余预算；超出部分先折叠成状态，再装最近 2 轮 | 复用 `foldDialogueState`，不要只靠静默丢轮次 |

静默丢轮次会让模型忘掉这个情境里已经做过的判断，又没有一份可核对的状态。人物分析会话因此必须折叠，不能只靠 `context-budget.ts` 从头部把旧轮次拿掉。

## 6. 明确不做

- 不把人物、心得、普通聊天收成一个记忆库。
- 不在这个功能里做双时态图、不每句话抽取实体。
- 不把模型的回复当作原文、简报或档案。自动更新只处理 `entries.jsonl` 里的新原文。
- 不用一条永远不关的会话装这个人的全部分析。
- 不把上一次会话再凝练一份，和简报并列。跨会话读档案、当前判断和简报路径。
- 默认不是隐私会话。要丢掉某次分析，删这条会话即可。

## 7. 落地顺序

### 阶段 1：这个人自己的会话

- 会话元数据增加 `personId`。此阶段不改 `fold`，不改 `prepareReflectionsContext`
- 人物页可以新建、切换、删除自己的分析会话；删除不影响 `people/<id>/`
- `GET /api/sessions` 不返回带 `personId` 的会话。按人物查询才返回
- join 带 `personId` 的会话时不写 `lastActiveSessionId`
- 桌面和移动端从人物页发送，都写入该人物的当前分析会话

验证：两个人各开两条会话，消息互不出现；删掉其中一条，档案、简报、原文仍在；全局聊天列表和 `lastActiveSessionId` 不变。桌面和移动端各走一遍发送。

### 阶段 2：发送即入库

- 人物页发送时，把用户输入追加到 `entries.jsonl`，再发起分析。落盘失败就不开始这一轮，并说明原因
- 过长输入在注入处截断，并写明全文本条 id。截断只影响注入，`entries.jsonl` 里仍是原话

验证：发送后立刻能在原文列表看到这条；会话文件写失败时原文仍在。

已落地：`people/input.ts` 的 `recordPersonInput` 负责「先落盘、再给注入版正文」，单条注入上限 8000 字；桌面在 `chatStart` 时就刷新原文列表，移动端在这一轮流结束后刷新。`kind=note`，不带 speaker。

### 阶段 3：会话内折叠

- `fold: true` 的人物会话走现有 `foldDialogueState`，阈值仍是待折叠内容超过 8000 token
- 四个小节不改。人物会话在提示词末尾加两句：用户明确否定过的回法写入「硬约束」并逐字保留；已经排除的回法写入「已定结论」，格式是「回法 + 为什么不要」
- 折叠提示里已有「被本批推翻的旧结论要删掉」，人物会话继续遵守，不在状态里并列两种说法
- 折叠状态按会话 id 存在现有 `dialogue-state.md`，只注入本会话的「当前有效」

验证：来回超过阈值后，窗口里的历史变短，会话文件里的旧消息还在；用户说过「不要直接否定」时，折叠状态的硬约束里仍有这句原话；新开的另一条会话看不到这条的折叠状态。

已落地：判据收敛为 `session.fold`，不再靠 `app_state.reflectionsSessionId` 旁路判断。人物会话在 `createSession` 时写 `fold: true`；心得会话在绑定接口（`POST /api/app-state/reflections-session`）补写。旧数据没有这个字段，装配时惰性补一次，行为与以前一致。人物会话在提示词末尾追加 `PERSON_FOLD_ADDENDUM` 两句（`chat/dialogue-fold.ts`）。测试 `chat/person-fold.test.ts` 覆盖：判据、两句提示词、状态按会话隔离、删会话清块、截断后游标归零。删人物会话连同「当前有效」块一起删；心得会话保留（那是人的长期结论）。

### 阶段 4：原文落盘后自动整理

- 阶段 2 写入新原文后跑整理
- 简报只追加；没有正文时跳过，不推进 `organizedAt`
- 同一次整理替换 `current.md`；超过 1500 字则不替换
- 自动路径不调用档案替换。人点「整理」时才允许 `<<<档案>>>`
- 手动「整理」按钮保留

验证：发送一段有实质内容的情境后，不点按钮，`digest.md` 末尾多出一段且旧段还在，`current.md` 被整篇换掉，`profile.md` 与发送前字节级一致；发送一句没有实质内容的问题，简报和当前判断都不变。

已落地。数据结构：`createPerson` 时写 `current.md`（只有版本头），`getPersonRecord` 返回 `{ person, profile, digest, current }`，旧目录缺这个文件按空处理。写入 `replaceCurrent` 只算正文（不含版本头），超过 1500 字返回 `written: false`、文件不动；简报照常追加、`organizedAt` 照常推进——plan 原文是「超出则这次不替换」，不是整轮失败。

触发：`processChatMessage` 在 `chatEnd` 推送之后 `void scheduleAutoOrganize(...)`，不 `await`。串行单位是 `personId`：`inFlight` 在第一次 `await` 之前同步占位，同一人并发只跑一份；手动「整理」期间（`markManualOrganize`）自动整理直接让路，不排队。模型走 `config.compaction`（后台、便宜那套），与手动整理用用户当前选的模型分开。

### 成本：三层节流

一开始是「每条有实质内容的消息之后跑一次」。用起来你会发现，一次闲聊能触发十几次同样的模型调用，而简报的增值边际递减得很快。现在是三层，按代价从大到小：

1. **每人每天一轮**（`autoOrganizeCadence`，默认 `daily`）。跑成功、跳过、失败都会在 `meta.json` 的 `organizeWindow.day` 写下北京日期；同一天再发消息直接返回 `already-today`，一次模型调用都不花。代价是「当天上午说过的事，下午的对话里模型看不到简报」，所以这一天的原文依然照常按条落盘（`entries.jsonl`），`organizedAt` 游标没前进，第二天那一轮会一次补齐——**不丢，只是晚**。切到 `message` 就是旧行为。
2. **防抖**（`autoOrganizeDebounceMs`，默认 8 秒）。连发三条只算一轮，且三句一起读。用 `debounceSince` 兜住「一直在打字」：从第一条消息算起最多等 45 秒（`DEBOUNCE_MAX_WAIT_MS`）就强行跑，不让简报饿一整个下午。排程和 `inFlight` 分开——计时期间不算「整理中」，界面不会空转。
3. **最小内容**（`autoOrganizeMinUnits`，**默认 0 = 关**）。新增原文折算后太短就不跑。默认关的理由：`daily` 节奏下一天最多省一次调用，但 40 个字能说完整一件事（「她周五要搬家，让我别提前问，也别告诉别人」只有 23 个字），这个门槛拦掉的多是真内容。而且提示词里已经写了「这次原文没有实质内容时只输出『无』」，模型自己就是更准的判断器。切到 `message`（每条消息都整理）时才建议打开，那时寒暄会成倍烧钱。**手动「整理」按钮从不走这个门槛**——人点了就是要整理，哪怕只有一句「在吗」。打开时按语言折算，不是裸字符数：中日韩每字算 1，拉丁字母/数字每 2 个算 1，空白标点不计。这样 `40` 大致等于「40 个汉字」或「80 个英文字母」，两者信息量才可比。跳过不占当天名额。

失败会占掉当天名额：否则模型挂掉的那个下午，每条消息都会重试一次同样的错误，一天烧几十次。真挂了看 `lastOrganize.message`。

粗略量级：一天聊 30 句、分 10 轮，旧行为 30 次调用；三层叠起来是 1 次（内容够的话），最多 2–3 次。手动「整理」按钮不受这三层限制，随时点随时跑。

并发与失败（补齐 review 发现的四个问题）：

1. **游标只前进。** `appendDigest` 写 `organizedAt` 时取「现有值」和「这次值」里较晚的一个。自动整理读了旧游标、调模型花了两分钟，期间手动整理已经把游标推到更远；旧实现会把它写回去，下一次整理把已经整理过的原文全部重做一遍。
2. **写入按人串行。** `store.ts` 的 `withPersonLock(personId, fn)` 串起 `appendDigest` 与 `recordOrganizeOutcome`。`digest.md` 是整篇读出→拼接→写回，自动与手动同时进来必然丢一段；`inFlight` 只管得住自动侧。
3. **手动整理取消在跑的那次自动整理。** `markManualOrganize(id, true)` 会 abort 对应的 `AbortController`，这次结果直接丢弃（`status: "cancelled"`），不写盘、不记失败，补跑也跳过——手动整理会把游标推到最新。取消信号用默认 `AbortError`：`fetchWithRetry` 只对 `name === "AbortError"` 立即停止重试，自定义 reason 会被当普通网络错误重试三轮。
4. **失败与超时看得见。** `meta.json` 加 `lastOrganize: { at, status, message }`（`ok` / `skipped` / `failed`），`GET /api/people/:id` 同时返回 `organizing`。总时长上限 60 秒，单次请求 45 秒（**必须短于总上限**，相等的话两个计时器同一刻触发，谁先到全凭运气）。到点 abort 并记「整理超时，没有写入」。失败或超时的那一轮**不补跑**：游标没前进，下一条消息会重新触发，此刻补只会立刻再撞一次同样的错误、再烧一次模型。桌面在分析条上显示一行状态，移动端在开关那一行右侧；服务端说还在跑时，两端都显示「整理中…」并每 1.5 秒重拉一次，不再让人对着旧简报猜。

提示词：自动版 `AUTO_ORGANIZE_INSTRUCTIONS` 不含「现有档案」，明确「不要写档案」，并要求 `<<<当前>>>` 之后给整篇当前判断；模型回「无」按无正文跳过。`applyAutoOrganizeResult` 与手动 `applyOrganizeResult` 分开：后者才调 `writeProfileIfComplete`，自动路径即使回复里带了 `<<<档案>>>` 也只取它前面的简报。流式气泡用 `visibleBeforeMarker`，`<<<当前>>>` 与 `<<<档案>>>` 都不会露出半个标记。

开关：`config.autoOrganize` 默认开；`app_state.autoOrganize` 是两端的用户覆盖，`GET /api/app-state` 返回合并后的 `autoOrganizeEffective`，`PUT /api/app-state/auto-organize` 写它。桌面在人物页分析条上，移动端在分析条第二行，都显示「开 / 关」。

注入：`buildPersonContextSuffix` 顺序为 档案 → 当前判断（整篇）→ 简报路径 → 原文路径；当前判断为空时整段略过，不占窗口。测试 `people/auto-organize.test.ts` 覆盖单次落盘、两轮只追加、无实质内容跳过、超限不替换、丢弃档案段、开关关闭、无新原文、手动优先、单人串行、失败留痕、跳过留痕、成功记完成时刻、手动取消在跑的那次、取消后不补跑、超时留痕、每天一轮、次日补齐积压、字数门槛不占名额、失败也占名额、连发防抖合并成一轮、最长等待算术；`people.test.ts` 覆盖 `current.md` 读写与上限、路径与注入、游标不回退、并发写不丢段、`lastOrganize` 与 `organizeWindow` 读写与老目录缺字段；`server/chat-handler-auto-organize.test.ts` 覆盖「`chatEnd` 已推送、整理在其后启动」与模型失败不影响原文，以及手动整理失败也留痕。
